# CameraAccess_AI — Project Report
**Date:** October 16, 2026  
**Project:** Meta Ray-Ban Glasses AI Analyst Integration  
**Platform:** Android (Kotlin + Jetpack Compose)

---

## 1. Overview

This project is an Android application that connects to **Meta Ray-Ban smart glasses** and uses the camera feed from those glasses to perform **real-time AI-powered scene analysis** using OpenAI's GPT-4o vision model.

The app is built on top of Meta's **Device Access Toolkit (DAT) SDK** — an official SDK that allows Android developers to receive live video, capture photos, and manage the connection state of Meta wearable devices. On top of this foundation, we designed and implemented a new AI feature that samples the live video stream and sends frames to an AI model for analysis, returning insights displayed as a live text overlay on the user's phone screen.

A key real-world use case for this feature is **nutritional analysis** — for example, a user wearing the glasses while eating can receive real-time AI commentary describing what food is present, estimating calories, macronutrients, and portion sizes based on what the camera sees.

## 2. What the App Does

### 2.1 Existing Features (pre-existing foundation)

The app originally included the following camera access capabilities, all of which were preserved unchanged:

| Feature | Description |
|---|---|
| **Live Stream** | Displays the real-time camera feed from the Ray-Ban glasses on the phone screen |
| **Photo Capture** | Captures high-resolution photos from the glasses (supports both Bitmap and HEIC formats with EXIF orientation correction) |
| **Video Recording** | Records the stream to an MP4 file using Android's MediaCodec (H.264 video + AAC audio), saved to the device gallery |
| **Face Blur** | Detects faces in the stream using Google ML Kit and applies a pixelation blur — toggleable by the user |
| **Media Import** | Imports photos and videos stored on the glasses |
| **Mock Device Kit** | A testing mode that simulates the glasses for development without physical hardware |

### 2.2 New Feature: AI Analyst Mode

The new **AI Analyst mode** is a completely separate operating mode within the same app. When the user selects it, the live camera feed from the glasses is sampled every 3 seconds and sent to OpenAI's GPT-4o model. The AI analyzes each frame and returns a short text response (2–3 sentences), which is displayed as a semi-transparent overlay card on the live video.

**Example interactions:**
- User points glasses at a plate of food → AI responds: *"I can see a grilled chicken sandwich with lettuce and tomato on a brioche bun. Estimated nutrition: ~480 calories, 35g protein, 42g carbohydrates, 14g fat."*
- User points glasses at a coffee cup → AI responds: *"This appears to be a medium latte, likely made with whole milk. Estimated: ~180 calories, 7g protein, 15g carbohydrates, 9g fat."*
- User looks at a street scene → AI responds: *"You're standing at what looks like a busy urban intersection. There's a café on the left and a pharmacy ahead."*

The user can also provide an optional **session context** before starting — for example: *"I am tracking my calorie intake today"* or *"Focus on identifying ingredients."* This context is sent alongside every frame analysis for the entire session, making the AI's responses more focused and relevant.

## 3. Architecture and Technical Design

### 3.1 Design Philosophy: Feature Isolation

A deliberate architectural decision was made to keep the AI feature **completely isolated** from the existing camera features. This follows the **Single Responsibility Principle** — each component does exactly one job. The existing stream, recording, and face blur code was never modified. The AI feature lives in its own package (`aistream/`) and only touches shared navigation code with minimal, surgical changes.

This means:
- A bug in the AI feature cannot break the basic camera stream
- The AI feature can be removed or replaced without touching existing code
- Each feature is independently understandable and testable

### 3.3 Data Flow

The complete journey from glasses to screen:

```
Meta Ray-Ban Glasses (camera sensor)
        ↓  Bluetooth
Android DAT SDK (VideoFrame in I420 YUV format)
        ↓
AIStreamViewModel.handleVideoFrame()
        ↓  YuvToBitmapConverter (I420 → ARGB Bitmap)
AIAnalystProcessor.process(bitmap)
        ↓  throttle check: has 3 seconds elapsed?
        ↓  compress to JPEG at 60% quality
        ↓  Base64 encode
        ↓  HTTP POST (OkHttp on IO thread)
OpenAI GPT-4o Vision API
        ↓  JSON response
AIStreamViewModel (onResult callback)
        ↓  update AIStreamUiState.aiAnalysisText
AIStreamScreen (Jetpack Compose)
        ↓  recompose automatically
Text overlay card on phone screen
```

### 3.4 The AI Analyst Processor

`AIAnalystProcessor.kt` is the core of the AI feature. Key design decisions:

**Throttling**: The processor receives every video frame (24 per second) but only acts on one frame every 3 seconds. This keeps API costs low (~$0.06/minute with GPT-4o) and prevents network requests from stacking up. If a request is still in-flight when the next interval arrives, that frame is silently skipped.

**Image compression**: Each frame is compressed to JPEG at 60% quality before being sent. This reduces payload size from a raw bitmap (~3MB) to approximately 40–80KB, dramatically improving upload speed without meaningfully impacting the AI's ability to understand the scene.

**Low-detail mode**: The API call uses `"detail": "low"`, which instructs OpenAI to analyze the image at 512×512 resolution internally. This costs approximately 3× less per image than high-detail mode and is perfectly sufficient for scene understanding tasks like food identification.

**Session context**: If the user typed an optional context before starting (e.g., "I am counting calories"), it is appended to every API request as extra instruction. This allows the AI to tailor its responses to the user's specific goal for the entire session.

**Thread safety**: The bitmap is compressed on the calling thread (before the coroutine launches) because the bitmap object is reused by the stream for subsequent frames. If compression were deferred to the background thread, the bitmap might already contain new pixel data by the time the coroutine executes — a subtle race condition that this design avoids.

### 3.5 The OpenAI API Request

Each analysis call sends the following to OpenAI's Chat Completions endpoint:

```
Model: gpt-4o
Max tokens: 120

System prompt:
  "You are an intelligent assistant with the vision of smart glasses.
   Describe what you see and provide useful insights.
   When food or drink is present, estimate its nutritional profile —
   calories, macros, portion size — even if uncertain.
   Make confident, educated guesses. 2–3 sentences max."

User message:
  [JPEG image, Base64 encoded, detail: low]
  + "What do you see? Analyze and share useful insights."
  + [optional: "Session context: {user's typed context}"]
```

### 3.6 Navigation

The app uses a state-driven navigation pattern. A single `WearablesUiState` object holds boolean flags that determine which screen is displayed:

```kotlin
when {
    uiState.isStreaming    → StreamScreen       // original camera mode
    uiState.isAIStreaming  → AIStreamScreen     // new AI analyst mode
    uiState.isImportingMedia → ImportMediaScreen
    uiState.isRegistered   → NonStreamScreen   // device connected, choose mode
    else                   → HomeScreen        // first-time registration
}
```

## 5. Key Engineering Decisions and Rationale

### Why GPT-4o and not a smaller model?
GPT-4o is the most capable multimodal model available with strong vision understanding. For tasks like estimating nutritional content from an image — which requires both visual recognition and domain knowledge — a capable model produces meaningfully better results than smaller alternatives.

### Why 3-second intervals?
This was chosen as a balance between responsiveness and cost/performance. At 1 second, the feature feels more live but costs 3× more and puts more pressure on the network. At 5 seconds, it feels sluggish. 3 seconds is long enough for the AI response to arrive before the next request fires, creating a natural rhythm.

### Why no video recording in AI mode?
AI mode is designed for a specific purpose: real-time analysis. Adding recording would increase complexity and CPU load without adding value to the core use case. A separate mode for "record + analyze after" could be added later as a distinct feature.

### Why store the session context in WearablesUiState?
The session context needs to survive from the `NonStreamScreen` (where it's typed) through to `AIStreamScreen` (where it's used). Since `WearablesUiState` is already the shared state that drives navigation between these screens, it is the natural place to carry this value — no additional state management infrastructure needed.

## 6. User Flow

```
1. Launch app
2. HomeScreen — register app with Meta AI (one-time)
3. NonStreamScreen — glasses connect via Bluetooth
4. User optionally types a session context:
   e.g. "I'm eating lunch, track my macros"
5. User taps "AI Analyst"
6. App requests camera permission from glasses
7. AIStreamScreen appears:
   - Live video feed from glasses fills the screen
   - "Analyzing…" indicator appears top-right
   - After ~3 seconds: first AI analysis card appears at top
   - Card updates every 3 seconds with new analysis
8. User taps "Stop AI Stream" to return to device selection
```

## 7. What Was Learned / Educational Value

This project demonstrates several software engineering concepts in a practical context:

- **Feature isolation and separation of concerns** — keeping new functionality from polluting existing, working code
- **Asynchronous programming** — handling a 24fps video stream while making network calls without blocking the UI
- **State-driven UI** — using a single source of truth (UiState) to drive all screen rendering decisions
- **API integration** — constructing multimodal API requests with image data, handling responses, managing costs through throttling
- **Race condition awareness** — understanding why the bitmap must be compressed before a coroutine is launched
- **Architectural decision-making** — evaluating tradeoffs (cost vs. responsiveness, simplicity vs. features) before writing code
